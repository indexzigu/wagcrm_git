# 직원 카톡 업로드 계정 만들기 (operator)

> 카톡 대화 txt 를 CRM 에 올리는 직원용 계정을 여는 절차다. 이 계정은 **업로드 화면
> 하나만** 볼 수 있고 셀러·캠페인·정산·매출·세무에는 접근하지 못한다.
> 구현 정본: `src/lib/auth-roles.ts`(허용 경로) · `src/lib/auth-allowlist.ts`(인가 판정) ·
> `src/lib/supabase/middleware.ts`(집행) · `/settings/accounts`(오너 조작 화면).

## 한눈에

| 단계 | 하는 사람 | 걸리는 곳 |
| --- | --- | --- |
| 1. 직원이 구글 로그인 1회 | 직원 | crm.ygrd.kr |
| 2. 「계정 관리」에서 operator 로 승인 | 오너 | CRM 화면 |

**환경변수도 재배포도 없다.** 계정을 열려면 직원이 **먼저** 로그인해야 한다 — Supabase
계정은 최초 로그인 시점에 생기고, 그전에는 승인할 대상이 존재하지 않는다.

⛔ **종전 절차(`ALLOWED_LOGIN_EMAILS` env 에 이메일 추가 → 재배포)는 폐기됐다.**
그 env 두 개(`ALLOWED_LOGIN_EMAILS` · `ADMIN_LOGIN_EMAILS`)는 2026-08-08 에 삭제됐고
코드가 더 이상 읽지 않는다. 지금 그 값을 넣어도 **아무 일도 일어나지 않는다.**

---

## 1. 직원이 구글 로그인한다

직원에게 전달할 안내:

1. https://crm.ygrd.kr 을 연다.
2. 「Google 계정으로 로그인」을 누른다.
3. 회사에서 쓸 지메일 계정을 고른다.

로그인하면 **「승인을 기다리는 중입니다」 화면**이 뜬다. 정상이다 — 아직 아무 데이터도
보이지 않는다. 이 상태에서 주소창에 다른 경로를 입력해도 같은 화면으로 되돌아온다.

직원이 어떤 계정으로 로그인했는지 오너에게 알려주게 한다(대기 목록에서 골라야 한다).

## 2. 오너가 승인한다

CRM → 설정 → **「계정 관리」**(`/settings/accounts`).

대기 중인 계정이 목록 맨 위에 「대기」 배지로 뜬다. 이메일을 확인하고 **「operator 승인」**
을 누른다.

⚠️ **「admin 승인」과 헷갈리지 말 것.** admin 은 셀러 실명·원가·마진·정산까지 전부 보는
전체 접근이다. 카톡 업로드만 맡길 직원은 반드시 **operator** 다.

승인은 **다음 요청부터 즉시 반영된다** — 직원이 재로그인할 필요 없이 화면을 새로고침하면
업로드 화면(`/assets/katalk`)이 뜬다.

✅ **완료 확인:** 직원 화면 왼쪽 메뉴에 「판매 관리」·「정산 관리」가 **보이지 않으면** 정상이다.
오너 화면의 계정 관리 표에서 그 계정이 「활성 / operator」로 보이는 것도 함께 확인한다.

---

## 나중에 필요할 때

- **직원을 admin 으로 올리기 / 내리기:** 계정 관리 표의 역할 변경 버튼을 누른다.
  누가 언제 바꿨는지 `grantedBy`·`grantedAt` 으로 함께 기록된다.
- **직원 계정 닫기:** 계정 관리 표에서 **「접근 회수」**. 그 계정은 다음 요청부터
  「접근 권한이 없습니다」 화면만 보게 되고, 다시 로그인해도 대기 목록에 재등장하지 않는다.
  마음이 바뀌면 같은 표에서 「다시 승인」할 수 있다.
- **모르는 사람이 대기 목록에 떴을 때:** 구글 계정만 있으면 누구나 로그인을 시도할 수 있고,
  그 시도가 대기 줄로 쌓인다. 데이터는 전혀 보이지 않으므로 위험하지 않다. **「거절」**
  로 치우면 된다.
- **operator 에게 화면을 하나 더 열기:** `src/lib/auth-roles.ts` 의
  `OPERATOR_ALLOWED_EXACT` 에 경로를 추가한다(화이트리스트라 코드 변경 없이는 안 열린다).
  그 화면이 부르는 API 경로도 함께 넣어야 한다.

## 알려진 제약 (의도된 것)

- **오너 2계정은 계정 관리 화면에서 변경할 수 없다**(「오너」로만 표시된다). 소스 상수
  (`src/lib/auth-allowlist.ts`)가 그 둘을 항상 admin 으로 고정하는 **바닥**이라, 오너가
  실수로 자기 접근을 끊는 경로를 구조적으로 없앤 것이다. 부작용으로 오너는 자기 계정으로
  operator 화면을 체험할 수 없다 — 확인이 필요하면 별도 계정을 operator 로 승인해서 본다.
- **자기 자신의 역할은 바꿀 수 없다**(자기 행은 「본인」으로 표시된다). UI 와 서버 양쪽에서
  막는다.
- **업로드 화면의 「귀속 대상 지정」 드롭다운이 직원에게는 보이지 않는다.** 그 목록이 곧
  전 거래처·셀러·캠페인 이름이라 열 수 없다. 직원은 그대로 업로드하고, 방이 어디에 속하는지는
  오너가 「방 관리」탭에서 지정한다. 미매핑 업로드는 정상 경로다.
- **직원은 「방 관리」탭을 볼 수 없다.**

## 배경 — 왜 `user_metadata` 가 아니라 `app_metadata` 인가

역할·승인 상태는 Supabase `app_metadata`(= `raw_app_meta_data`)에만 쓴다. `user_metadata`
는 **사용자 본인이** `supabase.auth.updateUser({ data: … })` 로 쓸 수 있어서(공개 anon key
+ 본인 세션이면 충분) 역할 출처로 쓰면 직원이 브라우저 콘솔 한 줄로 스스로 admin 이 된다.
계정 관리 화면과 미들웨어 모두 `app_metadata` 만 읽는다.

Supabase 대시보드에서 손으로 고쳐야 할 일은 이제 없다. 필요한 조작은 전부 화면에 있다.
